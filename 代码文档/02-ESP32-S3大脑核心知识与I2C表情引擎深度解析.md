## 一、工程架构与跨芯片通信规范

### 1.1 双芯片 Monorepo 目录设计
在本项目中，大脑（ESP32-S3，主控）与底盘（STM32，电机驱动）共同组成一个机器人整体。
```text
drone/
├── firmware_brain/      # ESP32-S3 大脑固件 (C++20 / ESP-IDF)
├── firmware_chassis/    # STM32 底盘固件 (C99 / Keil/GCC)
├── protocol/            # 双端共享的纯 C 语言通信协议头文件
├── 文档/                # 硬件接线与引脚分配文档
└── 代码文档/            # 技术手册与代码规范
```
- **核心思想**：避免“代码碎片化”。双端共用同一个 Git 仓库，确保修改协议时两边能瞬间同步，杜绝“上位机改了协议、下位机没改”导致的联调灾难。

### 1.2 跨芯片通信中的 C/C++ 混合编程 (`extern "C"`)
- **问题背景**：C++ 编译器为了支持函数重载，在编译后会对函数名进行“符号粉碎”（Name Mangling，例如 `void foo(int)` 可能会变成 `__Z3fooi`）；而 C 语言编译器编译出的符号就是 `foo`。
- **解决方案**：在 C++ 中引入纯 C 语言编写的协议头文件时，必须包裹 `extern "C"`：
  ```cpp
  extern "C" {
  #include "robot_protocol.h"
  }
  ```
  这告诉 C++ 编译器：“请用 C 语言规则处理这个头文件，不要粉碎符号”。

### 1.3 结构体内存对齐与通信大坑 (`#pragma pack(push, 1)`)
- **硬件机制**：32 位 CPU 默认倾向于 **4 字节对齐**（以 4 字节为单位读取内存速度最快）。如果一个结构体里有一个 `uint8_t`（1字节）后面跟着一个 `float`（4字节），编译器会在它们之间悄悄塞入 **3 个无意义的填充字节（Padding Bytes）**！
- **灾难场景**：如果 ESP32-S3 和 STM32 的编译器对齐策略不一致，发出来的字节流就会错位，导致下位机收到的速度、角度全是乱码。
- **企业级规范**：通信数据结构体必须强制 **1 字节单字节紧凑对齐**：
  ```c
  #pragma pack(push, 1)  // 强制 1 字节严格对齐，禁止填充空洞
  typedef struct {
      uint8_t  header;       // 1 字节 (0xAA)
      float    target_v;     // 4 字节
      float    target_w;     // 4 字节
      uint8_t  checksum;     // 1 字节
  } RobotCmdPacket_t;
  #pragma pack(pop)        // 恢复原有对齐
  ```

## 二、现代 C++ 在嵌入式中的核心实践

在资源受限的单片机上写 C++，核心原则是：**零运行时开销（Zero-overhead Abstraction）、极致类型安全、杜绝动态内存碎片**。

### 2.1 编译期常量计算 (`constexpr` vs `#define`)
- **传统 C 语言**：使用 `#define SCREEN_WIDTH 128`。宏只是单纯的文本替换，没有作用域限制，没有类型检查，容易引发全局宏污染。
- **现代 C++ 规范**：使用 `static constexpr uint8_t SCREEN_WIDTH = 128;`。
  - `constexpr` 告诉编译器该常量在**编译期**完成计算并直接嵌入机器指令；
  - 拥有严格的类型检查（`uint8_t`），且受类作用域（`OledDriver::`）保护。

### 2.2 引用传递 (`&`) 杜绝内存拷贝
在 `FaceEngine` 构造函数中：
```cpp
explicit FaceEngine(OledDriver& oled);
```
- **为什么要加 `&`（引用）？**
  - 如果不加 `&`（写成 `OledDriver oled`），C++ 会执行“值传递”，在内存中完整复制一份庞大的 `OledDriver` 对象（包含 1024 字节显存和通信句柄），不仅消耗宝贵的 SRAM，而且复制品上的画画操作根本不会反映到真实的屏幕上！
  - 加上 `&`，表情引擎直接绑定到真实的物理屏幕对象，**内存开销为 0**。
- **为什么要加 `explicit`？**
  - 禁止单参数构造函数的“隐式类型转换”，防止编译器在参数不匹配时自动做让人费解的隐式转换。

### 2.3 强类型枚举 (`enum class` vs `enum`)
- **传统 `enum` 的缺陷**：
  ```c
  enum Emotion { NORMAL, HAPPY }; // NORMAL 进入全局命名空间，极易与其他模块的 NORMAL 冲突
  int a = NORMAL;                 // 允许隐式转成 int，破坏类型安全
  ```
- **现代 C++ `enum class`**：
  ```cpp
  enum class EmotionState { NORMAL, HAPPY, LISTENING };
  EmotionState state = EmotionState::NORMAL; // 必须带作用域，绝不污染全局，禁止隐式转 int
  ```

### 2.4 面向对象分层解耦（高内聚、低耦合）
```text
┌──────────────────────────────────────────────────┐
│           main.cpp (主业务 / 状态机)              │
└─────────────────────────┬────────────────────────┘
                          │ 情绪控制 (setEmotion)
┌─────────────────────────▼────────────────────────┐
│     FaceEngine.cpp (表情引擎 / 眨眼数学模型)       │
└─────────────────────────┬────────────────────────┘
                          │ 几何绘图 (fillRoundRect)
┌─────────────────────────▼────────────────────────┐
│     OledDriver.cpp (底层驱动 / 1KB 显存缓冲区)     │
└─────────────────────────┬────────────────────────┘
                          │ 物理通信 (I2C Master Bus)
┌─────────────────────────▼────────────────────────┐
│               0.96 寸 OLED 硬件屏幕               │
└──────────────────────────────────────────────────┘
```
- **分层收益**：如果未来把 0.96寸 OLED 更换为 1.3寸 OLED 或 TFT 彩屏，**顶层的 `FaceEngine` 逻辑一行代码都不需要改**，只需重写底层驱动类即可！

## 三、ESP32-S3 硬件架构与 FreeRTOS 调度机制

### 3.1 双核 Xtensa LX7 架构分配
ESP32-S3 拥有两个运行在 240MHz 的 32 位 Xtensa 处理器核心：
- **CPU Core 0（系统核）**：留给高优先级、耗时且不可被打断的任务（如 Wi-Fi 协议栈、蓝牙、I2S 音频流录播 DMA 中断）。
- **CPU Core 1（控制核）**：专门负责用户业务逻辑（OLED 动画渲染、姿态解算、底盘串口通信）。

### 3.2 任务核绑定 (`xTaskCreatePinnedToCore`)
```cpp
xTaskCreatePinnedToCore(
    oledRenderTask,   // 任务入口函数
    "oled_task",      // 任务调试名称
    4096,             // 任务独立栈空间 (4096 字节)
    nullptr,          // 传入参数
    5,                // 任务优先级 (1~25，数值越大优先级越高)
    nullptr,          // 任务句柄
    1                 // 绑定运行在 CPU Core 1
);
```

### 3.3 16MB Flash 与 8MB Octal PSRAM 内存结构
- **内部 SRAM (~380 KB)**：速度极快，用于高频中断和内核关键运行。
- **外部 8MB Octal OPI PSRAM**：通过 8 根高速数据线挂载在芯片外部，容量巨大。未来我们存放语音识别模型（WakeNet / MultiNet）和音频流缓冲区，全部放在这 8MB PSRAM 中！

## 四、I2C 通信协议底层物理时序与 ESP-IDF 驱动

### 4.1 物理层原理：开漏输出 (Open-Drain) + 上拉电阻
- I2C 只需要两根线：
  - **`SDA`（Serial Data）**：双向串行数据线；
  - **`SCL`（Serial Clock）**：串行时钟线（由主机 ESP32-S3 发出节拍）。
- **电气特性**：两根线在空闲时全部被外部/内部上拉电阻拉到 **3.3V 高电平**；当芯片想要发送 `0` 时，内部晶体管导通拉低到地（GND）。这种设计支持多个设备挂在同一组线上而不会短路。

### 4.2 I2C 通信标准时序帧
```text
  SCL ──┐   ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐   ┌──
        └───┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └───┘  
  SDA ──┐     ┌───────────────────────┐   ┌───┐   ┌──
        └─────┴───────────────────────┴───┘   └───┘  
       START       7位从机地址(0x3C) + W(0)  ACK  STOP
```
1. **起始信号 (START)**：SCL 处于高电平时，SDA 突然从高跳变到低。
2. **寻址字节**：主机发送 7 位从机地址（`0x3C` 即 `0111100`）+ 第 8 位读写标志（`0` 代表写入）。
3. **应答信号 (ACK)**：从机（OLED）检测到自己的地址匹配后，在第 9 个时钟周期将 SDA 拉低，表示“我收到了”。
4. **数据传输**：每次传输 8 位数据，从机回 1 位 ACK。
5. **停止信号 (STOP)**：SCL 处于高电平时，SDA 从低跳变到高，总线释放。

### 4.3 ESP-IDF 5.x/6.x 新一代 Master Bus 驱动优势
- 早期 ESP-IDF 使用旧版 `i2c_driver_install`，配置繁琐且不支持现代总线多设备抽象。
- 新版采用 **Bus（总线）与 Device（挂载设备）分离架构**：
  ```cpp
  // 1. 创建 I2C 总线
  i2c_new_master_bus(&bus_cfg, &m_busHandle);
  // 2. 挂载 0x3C 的 OLED 设备
  i2c_master_bus_add_device(m_busHandle, &dev_cfg, &m_devHandle);
  // 3. 传输时只需操作设备句柄
  i2c_master_transmit(m_devHandle, buf, len, timeout_ms);
  ```

## 五、SSD1306 OLED 屏幕物理特性与显存映射算法

### 5.1 显存分页机制 (Page Addressing)
- 0.96 寸 OLED 分辨率为 **128 列 × 64 行**，共 8192 个像素。
- 硬件将 64 行分为 **8 个 Page（Page 0 ~ Page 7）**，每个 Page 高 8 个像素（正好对应 1 个字节 8 bit）：
  ```text
  Page 0 (行 0~7)   : [Byte 0] [Byte 1] ... [Byte 127]  --> 128 字节
  Page 1 (行 8~15)  : [Byte 128] [Byte 129] ... [Byte 255]
  ...
  Page 7 (行 56~63) : [Byte 896] ... [Byte 1023]
  --------------------------------------------------------
  全屏显存总计: 128 × 8 = 1024 字节 (1 KB)
  ```

### 5.2 像素点映射数学公式 (`drawPixel`)
当要在屏幕坐标 $(x, y)$ 处点亮一个像素时：
1. **计算所在的字节索引**：
   $$\text{index} = x + \left(\frac{y}{8}\right) \times 128$$
2. **计算在字节内部的第几位 (Bit Position)**：
   $$\text{bit\_pos} = y \pmod 8$$
3. **位运算操作**：
   - 点亮（置 1）：`m_buffer[index] |= (1 << bit_pos);`
   - 熄灭（清 0）：`m_buffer[index] &= ~(1 << bit_pos);`

### 5.3 为什么使用全屏帧缓冲 (FrameBuffer)？
- **如果直写屏幕**：每次画一个点就要发一次 I2C 寻址和命令，画一对眼睛需要通信数千次，屏幕会出现明显的从上到下扫描撕裂和闪烁，帧率不足 5 FPS。
- **全屏帧缓冲方案**：所有画线、画圆角矩形都在单片机的 1024 字节内存数组中以纳秒级速度完成，画好后通过 I2C **单次高速流式传输**送入屏幕，帧率高达 **30~50 FPS**，画质如丝般顺滑！

### 5.4 官方数据手册核心指令解析
| 指令十六进制 | 手册官方名称 | 功能解析 |
| :--- | :--- | :--- |
| `0xAE` | `Set Display OFF` | 进入休眠，关闭屏幕发光，防上电花屏闪烁 |
| `0xD5, 0x80` | `Set Display Clock Divide` | 设置时钟分频与振荡频率，锁定 370kHz 稳定帧频 |
| `0xA8, 0x3F` | `Set Multiplex Ratio` | 设置 64 路多路复用扫描（128x64 分辨率） |
| **`0x8D, 0x14`** | **`Charge Pump Setting`** | **最核心指令！开启芯片内置 7.5V 升压电荷泵（3.3V 供电下必开，否则不亮）** |
| `0x20, 0x00` | `Set Memory Addressing Mode` | 设置为水平寻址模式（写入后列自动+1，跨行自动换页） |
| `0xA1` | `Set Segment Re-map` | 水平左右镜像翻转，适配引脚朝上的正常视角 |
| `0xC8` | `Set COM Scan Direction` | 垂直上下反向扫描，与 0xA1 组合成正立显示 |
| `0xAF` | `Set Display ON` | 正式点亮面板 |

## 六、拟人动态表情引擎 (FaceEngine) 数学与算法设计

### 6.1 拟人眨眼时间状态机
- 现实生物眨眼具有**随机性**。
- 算法逻辑：
  ```cpp
  uint32_t now = getSystemTimeMs();
  if (!m_isBlinking && (now - m_lastBlinkTimeMs >= m_nextBlinkIntervalMs)) {
      m_isBlinking = true;
      m_blinkPhase = 0;
  }
  ```
- 每次眨眼完成后，生成下一次眨眼随机等待期：
  $$\text{Interval} = 2000\text{ms} + (\text{rand()} \pmod{2500})\text{ms} \quad (2.0\text{s} \sim 4.5\text{s})$$

### 6.2 眨眼帧高度与动态居中算法
- 眨眼过程由 6 帧关键高度组成：`{32, 20, 8, 3, 18, 32}`（单位：像素）。
- **动态居中公式**：
  $$\text{current\_y} = \text{EYE\_CENTER\_Y} - \frac{\text{current\_height}}{2} = 32 - \frac{h}{2}$$
- **效果**：眼睛在高度压缩变细的过程中，中心轴线始终稳定在 $Y=32$，呈现出眼睑从上下两侧向中间合拢的逼真视觉！

### 6.3 几何圆角矩形算法 (`fillRoundRect` / `drawRoundRect`)
- 利用勾股定理判定圆角边界：
  $$dx^2 + dy^2 \le r^2$$
- 中间画主体矩形，四个角根据距离公式计算圆弧像素，既保证了渲染效率，又画出了圆润灵动的机器人大眼睛。

## 七、嵌入式工具链与编译器底层原理解密

### 7.1 Docker 容器化跨平台编译的底层逻辑
- macOS 系统的默认编译器（Apple Clang）无法生成运行在 ESP32-S3（Xtensa 架构）或 STM32（ARM 架构）上的二进制机器码。
- 我们使用官方 Docker 镜像（内置 `xtensa-esp-elf-gcc/g++ 16.1.0`），将工程源码目录通过 `-v` 卷挂载到容器中，**实现了无论在 Mac、Windows 还是 Linux 上，编译结果 100% 绝对一致、零环境冲突**！

### 7.2 Clangd 跨架构索引与“ELF vs Mach-O”消除
- **痛点**：Zed 编辑器内置的 clangd 运行在 Mac 本地，默认使用苹果的 Mach-O 二进制规范，遇到单片机标准 ELF 段属性（如 `__attribute__((section(".iram1.text")))`）会误报“缺少逗号”。
- **解决方案**：在 [`.clangd`](file:///Users/mjt/Desktop/workplace/drone/.clangd) 中指定 `--target=arm-none-eabi`，将目标架构切换为嵌入式 ELF 目标，配合清洗 GCC 专有参数（`-mlongcalls`、`-fno-malloc-dce`），**彻底实现了编辑器 0 虚假报错、真实语法错误毫秒级精准标红！**
