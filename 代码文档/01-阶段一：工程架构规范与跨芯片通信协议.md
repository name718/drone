# 📚 阶段一：工程架构规范、跨芯片通信协议与开发环境建设

> **阶段目标**：建立企业级 Monorepo 多固件目录体系，制定双芯片通信协议，打通基于 Clangd 的编辑器开发环境。

---

## 1. Monorepo 多固件工程架构

在桌面自平衡机器人项目中，大脑（ESP32-S3，主控）与底盘（STM32，电机驱动）共同组成系统整体。

```text
drone/
├── firmware_brain/      # ESP32-S3 大脑固件 (C++20 / ESP-IDF)
├── firmware_chassis/    # STM32 底盘固件 (C99 / Keil & GCC)
├── protocol/            # 双端共享的纯 C 语言通信协议头文件
├── 文档/                # 硬件接线与引脚分配文档
└── 代码文档/            # 技术手册与开发规范
```

### 💡 核心设计思想：
- **消除代码碎片化**：上位机（大脑）与下位机（底盘）在同一个 Git 仓库中协同演进。
- **协议原子化同步**：通信协议文件位于根目录 `protocol/`，修改协议时双端实时同步，彻底杜绝“上位机改了协议、下位机没改”导致的联调灾难。

## 2. C/C++ 混合编程机制 (`extern "C"`)

### 2.1 符号粉碎 (Name Mangling) 原理
- **C++ 语言**：为了支持函数重载（Overloading），C++ 编译器在编译后会对函数名进行“符号粉碎”（例如 `void init(int)` 会被编译成 `_Z4initi`）。
- **C 语言**：C 语言编译器编译后的符号就是纯粹的函数名 `init`。

### 2.2 跨语言链接解决方案
为了让 ESP32-S3（C++ 代码）与 STM32（纯 C 代码）共享同一个协议头文件，必须在 C++ 端使用 `extern "C"` 显式包裹：

```cpp
extern "C" {
#include "robot_protocol.h"
}
```

这告诉 C++ 编译器：“请用纯 C 语言规则处理此头文件中的符号，禁止进行 Name Mangling”，确保双端链接无缝兼容。

## 3. 结构体单字节紧凑对齐与内存空洞解析

### 3.1 32位 CPU 的 4 字节默认对齐机制
32 位处理器（如 ARM Cortex-M 和 Xtensa LX7）默认以 **4 字节为边界** 读写内存，以追求最高的总线访问速度。

如果结构体成员如下定义：
```c
struct FaultyPacket {
    uint8_t  header;       // 1 字节
    // ⚠️ 编译器会在此处悄悄塞入 3 个无意义的填充字节 (Padding Bytes)！
    float    target_v;     // 4 字节
    float    target_w;     // 4 字节
    uint8_t  checksum;     // 1 字节
    // ⚠️ 编译器会在末尾塞入 3 个填充字节凑齐 4 的倍数！
};
```
原本只有 $1 + 4 + 4 + 1 = 10$ 字节的数据，在内存中实际占用了 **16 字节**！

### 3.2 跨单片机通信的致命隐患
如果 ESP32-S3 编译器与 STM32 编译器的填充策略稍有差异，发送方发出的字节流在接收方解析时就会发生**致命的相位错位**，导致目标速度、姿态角数据全部解析为乱码！

### 3.3 企业级解决方案 (`#pragma pack(push, 1)`)
所有跨芯片通信协议结构体必须强制 **1 字节单字节紧凑对齐**：

```c
#pragma pack(push, 1)  // 强制单字节对齐，严禁插入内存填充空洞
typedef struct {
    uint8_t  header;       // 1 字节 (固定 0xAA)
    float    target_v;     // 4 字节
    float    target_w;     // 4 字节
    uint8_t  checksum;     // 1 字节 (异或校验和)
} RobotCmdPacket_t;        // 严格精确为 10 字节
#pragma pack(pop)        // 恢复原有编译器对齐设置
```

## 4. 编辑器与 Clangd 跨架构索引深度调优

### 4.1 Mach-O vs ELF 段属性冲突
- **现象**：Zed 编辑器内置的 clangd 运行在 Mac 本地，默认以 macOS 的 Mach-O 二进制规范解析代码。遇到单片机标准 ELF 段属性（如 `__attribute__((section(".iram1.text")))`）时，会误报 `mach-o section specifier requires a segment and section separated by a comma`。
- **解决方案**：在 `.clangd` 中配置 `--target=arm-none-eabi`，将语法分析目标切换为嵌入式 ELF 规范。

### 4.2 GCC 专有参数清洗
单片机构建系统传递了大量 GCC/Xtensa 专属编译 Flag（如 `-mlongcalls`、`-fno-malloc-dce`），clangd 无法识别会满屏画红线。我们通过 `.clangd` 的 `Remove:` 规则将它们精准剔除。

### 4.3 去伪存真，恢复真实语法报错
- 配置 `UnusedIncludes: None` 屏蔽“头文件未使用”的强迫症黄色波浪线；
- **保留真实语法检测**：缺少分号、拼错变量名、函数参数不匹配、类型不兼容等**真实的 C/C++ 语法错误依然能在毫秒级精准画出红色波浪线！**
